# Оптимизация исполнения, 11 октября 2026

Основной горячий путь — Rust-движок: захват экрана и OpenCV-поиск иконок.
Изменения затрагивают выполнение, без перестановки файлов и изменения UI.

## Что изменено

- Сначала читаются пиксели. Области иконок копируются с GPU и передаются в
  OpenCV только для отслеживаний, у которых пиксельные условия выполнены.
  Пиксели и области читаются из одной удерживаемой текстуры кадра.
  Отслеживания только с иконками продолжают проверяться каждый опрос.
- GPU staging-текстуры сохраняются между cooldown и пропущенными проверками.
  Они удаляются при удалении иконки из конфигурации, освобождении экранной
  сессии и заменяются при изменении размеров области. Это обмен удерживаемой
  памяти на отсутствие повторного создания Direct3D-ресурсов.
- RGB строится прямо из mapped GPU-буфера с учётом RowPitch. Устранён
  промежуточный BGRA Vec: при трёх областях 1200 × 800 это 11,52 МБ временных
  выделений и копирования за опрос (3,84 МБ на одну область).
- На каждом тике больше не клонируются Icon и имя процесса, не выделяется
  отдельный массив RGB для каждого отслеживания.
- Неизменные хоткеи больше не вызывают две пересборки таблицы событий,
  блокировки её mutex, повторный разбор shortcuts и копирование списка в gate.
  Повторные попытки регистрации после отказа ОС и held-state сохранены.
- Сохранение неизменённого конфига не сериализует файл, не вызывает sync_all
  и не уведомляет подписчика. Clone для транзакции по-прежнему нужен.
- Изменения settings и другого профиля не отправляют активный профиль движку
  и не пересобирают его отслеживания. Порядок commit/notification сохранён.

## Замеры

Реальный DXGI/OpenCV, Windows, основной монитор 3440 × 1440,
release-профиль, по 100 опросов. Три области 1200 × 800, образцы 24 × 24.
p95 — время, в которое укладываются 95% измеренных опросов.

| Сценарий | p95 работы одного опроса |
| --- | ---: |
| До изменений: две точки и поиск во всех трёх областях | 242,81 мс |
| После: поиск во всех трёх областях всё ещё требуется | 237,71 мс |
| После: пиксельная часть AND не выполнена, три области пропущены | 2,370 мс |

В последнем сценарии измерен настоящий EngineCore + DXGI. Два взаимоисключающих
пиксельных условия в одной точке гарантируют отказ независимо от содержимого
рабочего стола. Проверено, что нет ROI-readback, поиска или задания действия.
Фактический интервал между опросами p95 — 50,578 мс.

Основной выигрыш — пропуск ненужных поисков (около 100 раз для измеренной
тяжёлой конфигурации). Это **не** ускорение самого алгоритма OpenCV в 100 раз:
если пиксели проходят или используются только иконки, большие области
по-прежнему не укладываются в 50 мс (100/100 превышений в замере).
Разница 242,81 → 237,71 мс мала и не доказывает устойчивого ускорения:
рабочий стол и нагрузка машины меняются между запусками. Удаление
промежуточного буфера подтверждает снижение аллокаций, а не отдельное
ускорение readback; его p95 в этих запусках — 15,23 и 17,15 мс.

Запуск измерения и Windows-проверки цветов/reuse/deletion:

```powershell
cargo test --release --manifest-path src-tauri/Cargo.toml --lib screen::tests:: -- --ignored --nocapture --skip saves_primary_screen_png
```

## Поведение и проверки

Пропущенный поиск не считается отсутствием иконки и не использует старую
оценку сходства. После прохождения пикселей поиск выполняется заново.
Ошибки файла образца и восстановление его доступности сообщаются только
при фактическом поиске; при невыполненных пикселях последнее состояние
ошибки остаётся прежним.

- Rust: 279 passed, 9 ignored. Отдельно два Windows-теста прошли в release.
- Frontend: 260 passed, 15 файлов; `npm run build` прошёл.
- Добавлены проверки независимых пиксельных диапазонов, icon-only/Absent,
  same-frame цветов, GPU reuse/deletion, no-op записи, порядка уведомлений,
  изменений чужого профиля и восстановления хоткеев после injection/отказа ОС.
- В исходном наборе исправлено устаревшее ожидание JSON без visualOrder;
  формат сериализации приложения не менялся.

## Другие найденные затраты

Frontend после большинства точечных mutations перечитывает весь список
профилей через IPC. Также IconRow загружает полный PNG ради проверки его
доступности. Эти пути требуют отдельного изменения контракта/проверок:
например, action_update возвращает Action, но одновременно может остановить
Tracker. Простая замена refetch на cache patch потеряла бы isRunning и
могла бы нарушить согласованность при конкурирующих изменениях.
