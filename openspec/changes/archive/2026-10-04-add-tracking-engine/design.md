# Design

## Context

Готовые части из предыдущих изменений:
- `ConfigStore` с профилями, трекерами, пикселями и действиями;
- модуль `screen` (`PrimaryScreen::read_pixels`) и модуль `foreground` из `add-pixel-capture`;
- `execute_key_sequence` с зависимостями `InputSink`, `Sleeper`, `Rng` из `add-key-sequence-action`;
- сценарий захвата пикселя, работающий как отдельная сессия.

Движок должен работать независимо от WebView: свёрнутое окно приложения тормозит JS-таймеры.

## Goals / Non-Goals

**Goals:**
- Стабильный период опроса 50 мс без накопления дрейфа.
- Логика срабатывания, проверяемая детерминированно, без реального экрана, ввода и времени.
- Один активный профиль и одно выполняемое действие в каждый момент.

**Non-Goals:**
- Статистика и журнал срабатываний.
- Настраиваемый период опроса.
- Работа нескольких профилей одновременно.

## Decisions

### 1. Три слоя: ядро, поток опроса, поток исполнителя

```
UI --invoke--> commands --EngineCommand--> [поток опроса]
                                             |  EngineCore (чистая логика)
                                             |  PrimaryScreen, foreground
                                             v
                                   mpsc (trackerId, Action)
                                             v
                                     [поток исполнителя] -- execute_key_sequence
                                             |
                                    ActionDone(trackerId) --> поток опроса
```

`EngineCore` — чистый конечный автомат без ввода-вывода:
- `tick(now, gameActive, samples)` возвращает список команд: какие точки читать, какие действия поставить в очередь;
- на входе также события `actionDone(trackerId, now)` и обновление конфигурации.

Поток опроса подставляет реальные `Instant`, `foreground` и `read_pixels`. Тесты подставляют фейковые.

Альтернатива — async-задачи на tokio. Отклонена: нужны точные `sleep` с `timeBeginPeriod(1)`, а планировщик tokio добавляет непредсказуемую задержку.

### 2. Состояния трекера в ядре

```
Polling --все пиксели прошли--> PreDelay{until = now + U(min,max)}
PreDelay --now >= until--> Queued  (действие отправлено исполнителю)
Queued --actionDone--> Resume{until = now + resumeDelayMs}
Resume --now >= until--> Polling
любое, кроме выполняемого --stop/deactivate--> снят с учёта
```

Исполнитель берёт действия из канала по одному в порядке FIFO. Это и есть общая очередь. Если трекер остановлен, пока его действие ждёт в канале, исполнитель пропускает действие по набору отменённых идентификаторов (`Arc<Mutex<HashSet<Uuid>>>`), не выполняя его.

Состояние `Queued` охватывает и ожидание в очереди, и выполнение. Трекер вернётся в `Polling` только через `actionDone`.

### 3. Тик опроса

Период 50 мс по дедлайнам: `next += 50ms; sleep_until(next)`. Если тик опоздал больше чем на период, `next` сбрасывается на `now`, пропущенные тики не догоняются.

На время активности движка (профиль активирован) действует `timeBeginPeriod(1)`.

В каждом тике:
1. Если активен захват пикселя или нет трекеров в `Polling`, чтение пропускается, обрабатываются только таймеры.
2. `foreground` сравнивает имя exe активного окна с процессом профиля без учёта регистра. Кэш по паре `(hwnd, pid)` избавляет от `OpenProcess` на каждом тике.
3. Игра активна: одним вызовом `read_pixels` читаются точки всех трекеров в `Polling`.
4. `EngineCore::tick` вычисляет совпадения и переходы.

Ошибка `read_pixels`, включая пересоздание дубликатора, означает пропуск тика без срабатываний.

### 4. Сравнение цвета

Чистая функция `pixel_passes(sample, pixel)`: совпадение, если `|Δc| * 100 <= tolerancePercent * 255` по каждому каналу. Целочисленное сравнение без плавающей точки эквивалентно `|Δc| <= tol × 255 / 100`. Затем применяется условие «равно» или «не равно».

### 5. Управление жизненным циклом

Команды:
- `engine_activate(profileId)` — деактивирует прежний профиль, если он был;
- `engine_deactivate()`;
- `tracker_set_running(profileId, trackerId, isRunning)` — сохраняет флаг; для неполного трекера возвращает ошибку.

`Tracker.isRunning` имеет `#[serde(default)]`.

`ConfigStore` после каждой мутации вызывает подписчика. Движок получает снимок профиля, если это активный профиль, и обновляет конфигурацию ядра. Трекеры с изменёнными настройками остаются в текущем состоянии, новые пиксели учитываются со следующего опроса.

`pixel_delete` и `action_update` сбрасывают `isRunning`, если трекер стал неполным. Удаление активного профиля деактивирует движок.

Сценарий захвата из `add-pixel-capture` выставляет флаг паузы движка (`AtomicBool`) на всё время сессии и снимает его при завершении или отмене.

### 6. Фронтенд

Маршруты профиля оборачиваются элементом-макетом `ProfileRoute`:
- при монтировании вызывает `engine_activate(profileId)`;
- при размонтировании вызывает `engine_deactivate()`.

Так переход между `ProfilePage` и `TrackerPage` того же профиля не прерывает работу, а возврат к списку профилей останавливает её.

Движок шлёт событие `engine://status` с полями `{ profileId, gameActive }` только при изменении. `ProfilePage` показывает индикатор с текстом и иконкой, когда есть запущенные трекеры.

Кнопка старта и остановки в строке трекера: `aria-pressed` и текстовая подпись состояния. Для неполного трекера кнопка недоступна, а пояснение связано через `aria-describedby`.

## Risks / Trade-offs

- [Сон потока опроса задерживается под нагрузкой] → тики по дедлайнам без догоняния; редкая задержка в один тик несущественна для срабатывания за 100 мс.
- [Действие из очереди выполняется после выхода пользователя из игры] → принято сознательно: перепроверки и прерывания нет. Выход из профиля или остановка отменяют ещё не начатые действия.
- [Гонка между остановкой трекера и стартом его действия у исполнителя] → проверка набора отменённых идентификаторов непосредственно перед `execute_key_sequence`. Если действие успело начаться, оно доводится до конца, как и требует спецификация.
- [WebView не размонтирует `ProfileRoute` при закрытии окна] → при закрытии процесс завершается, и движок останавливается вместе с ним. Флаги «запущено» уже сохранены.
