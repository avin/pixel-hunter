# Design

## Context

После `add-app-foundation` у трекера есть имя и настройки времени; `add-pixel-capture` добавляет пиксели. Здесь трекер получает действие. Вызов исполнителя по условию — задача `add-tracking-engine`. Это изменение поставляет модель, редактор и исполнитель с API, который движок вызывает напрямую.

Ограничения: никакой инъекции в процесс игры; приложение работает с правами администратора (UIPI не блокирует ввод в игры, запущенные от администратора).

## Goals / Non-Goals

**Goals:**
- Модель действия, в которую новый тип добавляется без изменения существующих.
- Ввод, который принимают игры на DirectInput и Raw Input.
- Исполнитель, проверяемый без реального ввода и реального времени.

**Non-Goals:**
- Кнопки мыши, клавиша Win, PrintScreen, удержание клавиш дольше одного нажатия.
- Изменение порядка шагов перетаскиванием.
- Различение левых и правых модификаторов в сочетаниях.
- Кнопка пробного запуска действия в UI.

## Decisions

### 1. Действие — размеченное объединение по `type`

Rust:

```
#[serde(tag = "type", rename_all = "camelCase")]
enum Action { KeySequence(KeySequenceAction) }

KeySequenceAction { steps: Vec<KeyStep> }
KeyStep  { id: Uuid, delayBeforeMs: Option<DelayRange>, combo: KeyCombo }
KeyCombo { modifiers: Vec<Modifier>, key: KeyCode }   // Modifier: ctrl | shift | alt
```

TS повторяет форму как дискриминированный union. `Tracker.action` имеет `#[serde(default)]`, по умолчанию `KeySequence { steps: [] }`.

Инвариант: у первого шага `delayBeforeMs = None`, у остальных `Some`. Rust нормализует его при каждом `action_update`: при удалении первого шага задержка нового первого отбрасывается.

`modifiers` хранятся в каноническом порядке Ctrl, Shift, Alt без повторов. Одиночный модификатор записывается как `key` (`ShiftLeft`) с пустым `modifiers`.

Команда `action_update(profileId, trackerId, action)` заменяет действие целиком: правки одного шага малы, а одна команда проще набора команд для отдельных шагов.

Альтернатива — общий список шагов с полем `type` у шага. Отклонена: пользователь хочет, чтобы у каждого действия была своя конфигурация, а не общий конструктор.

### 2. Реестр типов действий на фронтенде

В `TrackerPage/ActionSection/actionTypes.ts`:

```
actionTypes: Record<Action["type"], { label: string; createDefault(): Action; Editor: ComponentType<EditorProps> }>
```

`ActionSection` рендерит select по реестру и `Editor` выбранного типа. Новый тип означает новую запись в реестре и новый вариант enum.

Правило на будущее: при появлении второго типа смена типа с непустыми настройками требует подтверждения и заменяет настройки на `createDefault()`.

### 3. Коды клавиш: `KeyboardEvent.code` и одна таблица в Rust

Шаг хранит физический код клавиши (`KeyQ`, `Digit1`, `F5`, `ArrowUp`, `NumpadEnter`, `ShiftLeft`). Он не зависит от раскладки, что и нужно для игр. Rust держит таблицу `code → (scan code, extended)` вместе с подписью для UI. Команда `key_codes_list` отдаёт её фронтенду, чтобы запись отвергала неподдерживаемые клавиши, а `action_update` проверяет коды повторно.

Альтернатива — дублировать таблицу в TS. Отклонена: две копии расходятся.

### 4. Запись нажатия в WebView

`KeyRecorder` в режиме записи слушает `keydown`/`keyup` на `window` в фазе capture и вызывает `preventDefault` и `stopPropagation`. Так подавляются ускорители WebView2 (F5, Ctrl+R) и обработчики приложения. `repeat` игнорируется.
- Не-модификатор: сочетание из `ctrlKey`/`shiftKey`/`altKey` и `code`.
- Модификатор: ждём; если до его `keyup` не пришла другая клавиша, записываем сам модификатор.

Выход из режима записи: повторный клик по кнопке или `blur` кнопки.

Ограничения ОС: Alt+Tab, Alt+F4, Ctrl+Alt+Del, Win до WebView не доходят или обрабатываются системой. PrintScreen приходит только как `keyup`. Поэтому эти клавиши в список поддерживаемых не входят.

### 5. Исполнитель и ввод

`execute_key_sequence(action, input: &mut dyn InputSink, clock: &dyn Sleeper, rng: &mut impl Rng)`.

Настоящий `InputSink` отправляет события через `SendInput` с `KEYEVENTF_SCANCODE`, а для расширенных клавиш добавляет `KEYEVENTF_EXTENDEDKEY`. Модификаторы сочетаний отправляются левыми вариантами: Ctrl `0x1D`, Shift `0x2A`, Alt `0x38`.

Тайминги (константы в коде):

| Интервал | Диапазон | Распределение |
|---|---|---|
| Задержка перед шагом | из настроек шага | равномерное, целые мс |
| Удержание основной клавиши | 40–90 мс | колоколообразное |
| Между нажатиями модификаторов, между последним модификатором и клавишей, между отпусканиями | 15–35 мс | колоколообразное |

Колоколообразное распределение — среднее трёх равномерных величин (Ирвин — Холл), отображённое в диапазон.

На время выполнения действуют `timeBeginPeriod(1)` и `timeEndPeriod(1)` через RAII-guard: штатная гранулярность таймера Windows 15,6 мс съела бы разброс удержания.

Выбор `SendInput` со скан-кодами, а не с виртуальными кодами: многие игры читают клавиатуру через DirectInput и Raw Input по скан-кодам и игнорируют ввод с одними VK. Флаг «injected» у такого ввода остаётся. Это известный и принятый риск античитов.

## Risks / Trade-offs

- [Игра не реагирует на эмулированный ввод] → скан-коды и права администратора покрывают основные случаи. Остальное — защита игры, вне рамок изменения.
- [Залипшая клавиша, если процесс упал между «вниз» и «вверх»] → `panic = "abort"` в release не даёт выполнить cleanup. Окно удержания мало (до 90 мс), а повторное нажатие клавиши пользователем снимает залипание. Принимаем.
- [Неточность `Sleep` даже с `timeBeginPeriod(1)`] → погрешность 1–2 мс несущественна на фоне диапазонов 15–90 мс.
- [Пользователь ожидает раскладко-зависимую клавишу] → в UI подписи показывают физическую клавишу US-раскладки, например `Q`, а не `Й`.
