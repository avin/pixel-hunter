# Поведенческие тесты

## 1. Определи контракт и уровень

Сформулируй проверяемое публичное поведение одним предложением и выбери самый низкий уровень, на котором это поведение надёжно наблюдается:

- чистая функция или reducer — unit test;
- поведение одного компонента — Testing Library;
- связка компонентов и Redux — integration test через Testing Library с реальными Provider и store;
- Tauri-команда или внешний сервис — стаб или мок на собственной границе.

Шаг завершён, когда названы наблюдаемый результат и минимальная среда, в которой он проявляется.

## 2. Собери доказательство

- Для дефекта сначала воспроизведи симптом минимальным падающим тестом на выбранном уровне; он должен падать по причине дефекта.
- Для нового или исправленного поведения при практической возможности подтверди, что тест падает без целевой реализации.
- Фикстура включает минимум реального контекста, необходимого для контракта. Подменяй только внешние зависимости на публичной границе; внутренние компоненты и детали хранения оставляй реальными.

## 3. Проверь публичное поведение

- Элементы запрашивай по роли и доступному имени: `screen.getByRole("button", { name: "Pay now" })`.
- Взаимодействие выполняй через `userEvent` из `@testing-library/user-event`.
- Асинхронный переход ожидай через наблюдаемое состояние UI с `findBy...` или `waitFor`.
- Колбэки наблюдай через `vi.fn()` и `toHaveBeenCalled` / `toHaveBeenCalledOnce`.
- Описания `describe` / `it` держи короткими и поведенческими.
- Ожидания опираются на публичный результат; снапшоты, классы, testid, искусственные задержки и детали реализации не служат основным доказательством.

## 4. Закрой матрицу состояний

Проверь каждое состояние, которое поддерживает целевой код и которое меняет публичное поведение:

- loading, успешный результат, empty и восстанавливаемая ошибка;
- для формы возьми контракт показа ошибок из [`react-components`](../react-components/SKILL.md) и покрой каждую смену видимости, включая первый `blur`, попытку отправки, живое исправление и повторную ошибку, а также сброс состояния;
- клавиатурное управление и доступные имена интерактивных компонентов.

Каждый добавленный сценарий должен подтверждать отдельную ветвь поведения, а не повторять уже доказанное.

## 5. Верифицируй

Сначала запусти минимальный целевой тест, затем все подходящие проверки проекта. Тестовая работа завершена, когда каждый заявленный публичный результат наблюдается на минимальном достаточном уровне и все подходящие проверки проходят.
