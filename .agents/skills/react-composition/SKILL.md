# Композиция React-компонента

Цель — самый простой API, который выражает все текущие сценарии и делает невозможные сочетания невыразимыми.

## 1. Составь карту сценариев

- Найди всех текущих потребителей компонента.
- Для каждого зафиксируй режим, обязательные данные, владельца состояния и часть структуры, которой должен управлять потребитель.

Шаг завершён, когда каждое существующее место вызова сопоставлено с одним сценарием, а различия между сценариями названы.

## 2. Выбери форму API

Выбери первую форму, которая полностью покрывает карту сценариев:

1. Один прямой component API для одного сценария.
2. `variant` для небольшого закрытого набора визуальных вариантов одной сущности. Семантические состояния `disabled`, `loading` и `required` остаются boolean-props.
3. Отдельные компоненты, когда режимы заметно различаются составом, поведением или обязательными данными.
4. `children` или явные слоты, когда потребитель управляет структурой содержимого. Render prop оправдан, когда обычная композиция не передаёт нужное состояние или поведение.
5. Compound API, когда части образуют один виджет, координируют общее состояние, а потребителю нужно менять их состав или порядок.

У выбранной формы каждый уровень абстракции должен иметь текущего потребителя.

## 3. Определи владельца состояния

- Локальное состояние держи у ближайшего реального владельца.
- Context применяй для согласованной работы частей одного сложного виджета.
- Если UI должен работать с разными владельцами состояния, отдели интерфейс контекста от хранения.
- Одно состояние имеет один источник истины в Provider, Redux или локальном компоненте.

Шаг завершён, когда для каждого изменяемого состояния назван единственный владелец и путь данных ко всем потребителям.

## 4. Проверь решение

Завершай рефакторинг, только когда все условия выполнены:

- каждый текущий сценарий выражается публичным API;
- невозможные сочетания режимов исключены типами или структурой API;
- простой сценарий остаётся коротким и очевидным;
- в compound API есть один явный Provider/Root, небольшой публичный набор частей и понятная ошибка при их использовании вне владельца;
- доступность сохраняется в каждой допустимой композиции;
- публичное поведение тестируется без знания внутренней композиции, включая минимум один альтернативный реальный состав для compound API.
